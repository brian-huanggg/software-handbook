# AI 應用工程目錄

本軌道回答「怎麼用模型做出可靠的產品」：從第一次呼叫 LLM API 開始，到 RAG、評估、正式環境上線，最後自架開源模型。
讀者是會寫後端服務的工程師，不需要先讀理論基礎軌道。主要語言是 **Python**（FastAPI、Pydantic、pytest），專案用 `uv` 管理。

**先修**：會寫基本的 Python、懂 HTTP API 是什麼（後端領域 L1 的 1.2 有完整說明）。

**同一個 AI 領域的其他軌道**：遇到「為什麼 temperature 會影響輸出」這類問題，文中會連回理論基礎軌道（`docs/contents/ai/foundations.md`）；本軌道是代理人軌道（`docs/contents/ai/ai-agents.md`）的先修。

**模型與成本**：範例預設用本機 Ollama 跑開源模型，免費且可離線；需要更強的模型時改接商用 API，文中會標出哪些練習會產生費用與大約金額。

**貫穿的例子：手冊問答助理**。讀者用本手冊自己的文章當知識庫，一步步做出一個能回答問題、附上出處的問答服務：

- L1：直接把問題丟給模型，看見它的能力與幻覺。
- L2：加上檢索（RAG），讓回答有根據、附上出處。
- L3：加上評估資料集、快取與防護，讓它可以上線。
- L4：改用自架模型，部署到 k3s，並監控品質與成本。

| 層級 | 主題 | 讀完你能做到 |
| --- | --- | --- |
| L1 呼叫模型 | LLM API、提示工程、結構化輸出、串流、token 與成本 | 把 LLM 接進一個服務，並控制它的輸出格式 |
| L2 檢索增強 | 嵌入、向量資料庫、RAG、文件處理 | 做出一個有根據、附出處的問答系統 |
| L3 品質與上線 | 評估、防護、快取、延遲、可觀測性 | 證明系統夠好，並讓它穩定在正式環境運作 |
| L4 自架與架構 | 自架模型、GPU 規劃、微調的時機、成本架構、治理 | 為一個 AI 產品選擇模型與部署架構，並為成本負責 |

寫目錄時沿用本檔格式：`##` 為層級、`### <節號> <名稱>` 為節、`- [ ]` 為文章。
每新增一節，同時在 `site/src/sidebar/ai.ts` 的 `engineering` 軌道加上該節的標籤與目錄名稱。

## L1 呼叫模型：把 LLM 接進你的程式

L1 的目標是寫出一個呼叫 LLM 的小服務，並能控制它回傳什麼、花多少錢。

### 1.1 LLM 是什麼（給工程師的版本）

- [ ] LLM 能做什麼、不能做什麼
- [ ] token、上下文視窗與「下一個 token 預測」
- [ ] 模型的種類：大小、開源與閉源、推理模型
- [ ] 怎麼選模型：能力、速度、價格、授權
- [ ] 用 Ollama 在本機跑第一個模型

### 1.2 呼叫 LLM API

- [ ] 第一個請求：messages、角色與參數
- [ ] system prompt 與多輪對話
- [ ] temperature、top-p 與最大輸出長度
- [ ] 串流回應：SSE 與逐字顯示
- [ ] 錯誤、重試、逾時與速率限制
- [ ] 用 FastAPI 包成一個 HTTP 服務
- [ ] 金鑰管理：不要把 API key 寫進程式碼

### 1.3 提示工程

- [ ] 寫出清楚的指示：角色、任務、格式、限制
- [ ] few-shot：用範例教模型
- [ ] 思維鏈與讓模型先思考
- [ ] 提示模板與版本管理
- [ ] 常見失敗：指示衝突、太長的提示、模糊的要求

### 1.4 結構化輸出

- [ ] 為什麼需要結構化輸出
- [ ] JSON 模式與 JSON Schema
- [ ] 用 Pydantic 定義與驗證輸出
- [ ] 資訊擷取：從非結構化文字取出欄位
- [ ] 分類與路由：讓 LLM 做決策
- [ ] 驗證失敗時的處理策略

### 1.5 token 與成本

- [ ] 計算 token 數
- [ ] 輸入、輸出與快取 token 的價格
- [ ] 估算一個功能的每月成本
- [ ] 降低成本：縮短提示、選小模型、批次 API
- [ ] 提示快取（prompt caching）

## L2 檢索增強：讓模型根據你的資料回答

L2 的目標是讓手冊問答助理只根據手冊內容回答，並附上出處。

### 2.1 嵌入與語意搜尋

- [ ] 嵌入模型：把文字變成向量
- [ ] 相似度：餘弦、內積與歐氏距離
- [ ] 語意搜尋 vs 關鍵字搜尋
- [ ] 選擇嵌入模型：語言、維度、成本
- [ ] 用 NumPy 做出最小的語意搜尋

### 2.2 向量資料庫

- [ ] 為什麼需要向量資料庫
- [ ] 近似最近鄰（ANN）：HNSW 與 IVF 的直覺
- [ ] pgvector：在 PostgreSQL 裡存向量
- [ ] 專用向量資料庫：Qdrant、Chroma 等的取捨
- [ ] metadata 過濾與多租戶

### 2.3 文件處理

- [ ] 載入 Markdown、HTML、PDF
- [ ] 切塊（chunking）策略：固定長度、依結構、語意切塊
- [ ] 塊大小與重疊的取捨
- [ ] 保留出處：標題、路徑、行號
- [ ] 增量索引：文件更新時只重算變動的部分

### 2.4 RAG 系統

- [ ] RAG 的架構：索引、檢索、生成
- [ ] 把檢索結果放進提示
- [ ] 附上出處與引用
- [ ] 「不知道」：沒有根據時拒絕回答
- [ ] 實作手冊問答助理 v1

### 2.5 進階檢索

- [ ] 混合搜尋：BM25 加向量
- [ ] 重新排序（reranking）
- [ ] 查詢改寫與多重查詢
- [ ] 父子塊與上下文擴展
- [ ] 什麼時候不需要 RAG：長上下文與其他做法

## L3 品質與上線：證明它夠好，並讓它穩定運作

L3 的目標是用數字回答「這個 AI 功能夠好了嗎」，並讓它在正式環境安全、快速、看得見。

### 3.1 評估

- [ ] 為什麼 LLM 應用特別需要評估
- [ ] 建立評估資料集：從真實問題開始
- [ ] 規則式評估：精確比對、格式、關鍵字
- [ ] LLM-as-judge：用模型評估模型
- [ ] 評估 RAG：檢索品質與回答忠實度
- [ ] 人工評估與標註流程

### 3.2 評估驅動開發

- [ ] 線上評估：使用者回饋與 A/B 測試

### 3.3 防護與安全

### 3.4 效能與可靠性
