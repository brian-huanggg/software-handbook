# 測試與品質目錄

本領域寫給想成為**資深 QA 專家**的工程師：不只會寫自動化測試，還能判斷該測什麼、測到什麼程度、怎麼讓整個團隊對品質負責。
主要語言是 Go；測試工具盡量選 Go 生態系（`testing`、Testcontainers for Go、Pact Go、`playwright-go`、vegeta、godog），少數非 Go 工具（k6、axe-core）會說明為什麼選它。

**先修**：後端領域 L1（`docs/contents/backend.md`）。本領域假設你會寫 Go、會用 `testing` 套件寫基本的單元測試；語法層面的東西不再重講，只在需要時連回去。

**兩個受測系統（SUT）**：

- **短網址服務**：後端領域自己寫的 API，用來練單元、整合、契約、API、效能測試。你看得到也改得動它的每一行程式碼。
- **Gitea**：熱門的開源 Git 服務（Go 後端 + Web 前端），用來練 UI、E2E、探索式、無障礙測試。它可以用單一執行檔加 SQLite 在本機跑起來，而且 repo 裡有真實的 Playwright E2E 測試可以讀。這是「測一個不是你寫的系統」的練習。

| 層級 | 主題 | 讀完你能做到 |
| --- | --- | --- |
| L0 品質思維 | 測試的目的、缺陷成本、QA 的角色、測試原則 | 說清楚一個測試在保護什麼 |
| L1 測試設計 | 黑箱與白箱技術、探索式測試、缺陷報告 | 有系統地設計測試案例，寫出讓人修得動的缺陷報告 |
| L2 自動化分層 | 單元、整合、契約、API、UI 與 E2E | 為每一種風險選對測試層級並實作 |
| L3 測試套件工程 | 測試資料與環境、不穩定測試、覆蓋率與變異測試、CI 品質閘門 | 讓一套持續長大的測試保持可信又快速 |
| L4 非功能與品質策略 | 效能、韌性、安全、無障礙、正式環境測試、帶領品質工作 | 為一個產品擬定並推動品質策略 |

> 本領域的安全測試只講到「QA 在流程裡要涵蓋什麼」的程度；攻擊手法與滲透測試在資安領域（`docs/contents/cyber.md`）。
> CI 流水線怎麼建、部署策略怎麼運作在 DevOps 領域；本領域只講測試怎麼接進去、閘門怎麼設。

寫目錄時沿用本檔格式：`##` 為層級、`### <節號> <名稱>` 為節、`- [ ]` 為文章。
每新增一節，同時在 `site/src/sidebar/testing.ts` 加上該節的標籤與目錄名稱。

## L0 品質思維：先知道測試在保護什麼

在學任何技術之前，先建立判斷力：測試是為了降低風險、提供回饋，不是為了湊數字。

### 0.1 品質是什麼

- [ ] 品質的多個面向：功能、可靠性、效能、易用性、安全（ISO 25010 導覽）
- [ ] 錯誤、缺陷、失效：三個常被混用的詞
- [ ] 缺陷的成本：越晚發現越貴的原因與例外
- [ ] 驗證（verification）與確認（validation）

### 0.2 QA 的角色

- [ ] QA、QC、測試：三者的差別
- [ ] QA 在軟體生命週期裡的位置：從需求到上線後
- [ ] 左移（shift-left）與右移（shift-right）
- [ ] 從測試執行者到品質教練：資深 QA 的職責樣貌

### 0.3 測試的基本原則

- [ ] 七大測試原則：窮舉不可能、缺陷群聚、殺蟲劑悖論……
- [ ] 測試層級與測試類型：兩個常被混為一談的維度
- [ ] 測試金字塔、測試獎盃與它們的適用前提
- [ ] 測試先知（test oracle）：你怎麼知道結果是對的

### 0.4 小結

- [ ] 讀懂短網址服務與 Gitea：畫出兩個受測系統的功能與風險地圖

## L1 測試設計：有系統地想出測試案例

憑直覺寫測試會漏掉邊界、重複測同一件事。這一層學經典的設計技術，並用 Go 的 table-driven tests 把它們落地。

### 1.1 從需求開始

- [ ] 需求分析：找出模糊、矛盾、缺漏的地方
- [ ] 驗收條件與 Given-When-Then
- [ ] 需求可追溯性：需求、測試、缺陷怎麼對起來
- [ ] 參與需求討論：QA 在 refinement 會議該問的問題

### 1.2 黑箱測試技術

- [ ] 等價類劃分
- [ ] 邊界值分析
- [ ] 決策表
- [ ] 狀態轉移測試
- [ ] 組合測試與 pairwise
- [ ] 用例與使用者旅程測試
- [ ] 把設計技術寫成 Go 的 table-driven tests

### 1.3 白箱測試技術

- [ ] 敘述、分支、條件覆蓋
- [ ] 路徑與 MC/DC 的概念
- [ ] 用 `go test -cover` 看見沒被執行的程式碼
- [ ] 白箱測試的極限：覆蓋到不等於測到

### 1.4 經驗式與探索式測試

- [ ] 錯誤猜測與常見缺陷清單
- [ ] 探索式測試：章程（charter）、時間盒、測試筆記
- [ ] 啟發法與漫遊（tours）：在 Gitea 上做一次探索式測試
- [ ] 什麼時候手動測試比自動化更值得

### 1.5 缺陷管理

- [ ] 一份好的缺陷報告：重現步驟、預期與實際、環境、證據
- [ ] 嚴重度與優先級：誰決定、怎麼決定
- [ ] 缺陷生命週期與分類（triage）
- [ ] 根因分析：從一個缺陷看到一類缺陷

### 1.6 小結

- [ ] 為短網址服務的「建立短網址」寫出完整測試設計，並在 Gitea 提交三份缺陷報告

## L2 自動化分層：為每一種風險選對層級

自動化不是把手動步驟錄下來。這一層一層往上走，每一層都說清楚它抓得到什麼、抓不到什麼、成本是多少。

### 2.1 單元測試進階

- [ ] 好的單元測試：快速、獨立、可重複、自我驗證
- [ ] 斷言風格：標準庫、`go-cmp`、testify 的取捨
- [ ] 測試替身全貌：dummy、stub、spy、mock、fake
- [ ] 為可測試性設計：依賴注入、介面邊界、時間與亂數的控制
- [ ] Golden file 測試
- [ ] 測試程式碼也是程式碼：命名、結構、重構

### 2.2 整合測試

- [ ] 整合測試的範圍：要真的接什麼、要假的接什麼
- [x] Testcontainers for Go：真資料庫測試 → [文章](../../site/src/content/docs/testing/l2/2-2-integration-testing/testcontainers-go.md)
- [ ] 測外部 HTTP 依賴：`httptest.Server` 與錄放
- [ ] 測試訊息佇列與非同步流程
- [ ] build tag 與 `testing.Short()`：分開快測試與慢測試

### 2.3 API 測試

- [ ] API 測試要驗什麼：狀態碼、結構、語意、錯誤路徑
- [ ] 以 OpenAPI 規格驅動測試與驗證回應結構
- [ ] 用 Go 寫黑箱 API 測試套件：對著跑起來的服務測
- [ ] 認證、冪等性、分頁、限流的測試重點
- [ ] 測 Gitea 的 REST API：讀別人的 API 文件找測試點

### 2.4 契約測試

- [ ] 為什麼整合測試在微服務之間不夠用
- [ ] 消費者驅動契約：Pact 的概念
- [ ] Pact Go：在短網址的寫入與讀取服務之間建立契約
- [ ] 契約的版本管理與 can-i-deploy

### 2.5 UI 與 E2E 測試

- [ ] E2E 測試該涵蓋什麼：關鍵使用者旅程，而不是所有按鈕
- [ ] 在本機與容器中跑起 Gitea 作為受測系統
- [ ] `playwright-go`：選擇器、自動等待、斷言
- [ ] Page Object 與 Screenplay 模式
- [ ] 讀 Gitea 自己的 Playwright E2E 測試：專案怎麼組織它們
- [ ] 視覺回歸測試：截圖比對與它的雜訊
- [ ] 跨瀏覽器與響應式測試

### 2.6 行為驅動開發（BDD）

- [ ] BDD 的本質是溝通，不是工具
- [ ] Gherkin 與活文件
- [ ] godog：讓 Given-When-Then 成為可執行規格
- [ ] BDD 什麼時候會變成負擔

### 2.7 小結

- [ ] 為短網址服務建立分層測試套件，並為 Gitea 的「建立 repo → 開 issue → 關 issue」寫一條 E2E

## L3 測試套件工程：讓測試可信又快速

測試越多，維護成本、執行時間、不穩定的問題就越大。這一層把測試套件當成一個需要工程投入的產品。

### 3.1 測試資料管理

- [ ] 測試資料的來源：fixture、factory、builder、匿名化的正式資料
- [ ] 每個測試自己準備資料：隔離與清理策略
- [ ] 資料庫狀態：交易回滾、truncate、每測試一個 schema
- [ ] 個資與測試資料的合規問題

### 3.2 測試環境

- [ ] 環境的層次：本機、CI、共用測試環境、預備環境（staging）
- [ ] 用 docker compose 一鍵起整套受測系統
- [ ] 臨時環境（ephemeral environment）與每個 PR 一套環境
- [ ] 服務虛擬化與 mock server：依賴還沒好時怎麼測

### 3.3 不穩定測試（flaky tests）

- [ ] flaky 的常見根因：時間、順序、並行、外部依賴、等待
- [ ] 用 `go test -count`、`-shuffle`、`-race` 揪出 flaky
- [ ] 隔離（quarantine）政策與追蹤
- [ ] UI 測試的穩定性：等待策略與選擇器策略

### 3.4 衡量測試的有效性

- [ ] 覆蓋率能說明什麼、不能說明什麼
- [ ] 變異測試：用 gremlins 檢查測試真的會失敗
- [ ] 缺陷逃逸率與其他測試指標
- [ ] 刪掉測試：什麼樣的測試不值得留

### 3.5 測試速度與規模

- [ ] 測試的並行化：`t.Parallel()` 與它的陷阱
- [ ] 測試選擇與基於變更的測試
- [ ] 分片（sharding）與快取
- [ ] 測試金字塔失衡的症狀與修正

### 3.6 接進 CI 與品質閘門

- [ ] 測試在流水線中的位置：提交前、PR、合併後、夜間
- [ ] 品質閘門：哪些失敗應該擋下合併
- [ ] 測試報告：JUnit XML、趨勢、失敗分析
- [ ] 靜態分析作為品質工具：`go vet`、staticcheck、golangci-lint

### 3.7 小結

- [ ] 為短網址服務建一條 CI 測試流水線：分層執行、flaky 隔離、變異測試報告

## L4 非功能與品質策略：為產品的品質負責

資深 QA 的價值在於看見功能測試看不到的風險，並讓整個組織用對的方式投入品質。

### 4.1 效能測試

- [ ] 效能測試的類型：負載、壓力、浸泡、尖峰、容量
- [ ] 定義效能需求：延遲百分位、吞吐、錯誤率與 SLO
- [ ] 用 vegeta 對短網址服務施壓
- [ ] 用 k6 寫情境式負載測試（以及 xk6 的 Go 擴充）
- [ ] 讀懂結果：協調遺漏（coordinated omission）與常見誤判
- [ ] 前端效能：Core Web Vitals 與 Lighthouse

### 4.2 進階自動化技術

- [ ] 模糊測試：Go 原生的 `go test -fuzz`
- [ ] 基於性質的測試：rapid
- [ ] 基於模型的測試：從狀態機自動產生案例
- [ ] AI 輔助測試：產生案例、維護選擇器，以及它的限制

### 4.3 韌性與可靠性測試

- [ ] 混沌工程的原則與實驗設計
- [ ] 故障注入：延遲、錯誤、依賴中斷
- [ ] 災難復原與備份還原的驗證
- [ ] 升級與資料遷移的測試

### 4.4 安全與無障礙測試

- [ ] QA 的安全測試範圍：OWASP Top 10 檢查清單與安全需求
- [ ] 依賴與映像掃描：`govulncheck` 與 SCA
- [ ] 動態掃描（DAST）接進流水線
- [ ] 無障礙測試：WCAG、axe-core、鍵盤與螢幕閱讀器的手動檢查
- [ ] 在 Gitea 上做一次無障礙稽核

### 4.5 在正式環境中測試

- [ ] 為什麼預備環境永遠不等於正式環境
- [ ] 合成監控（synthetic monitoring）
- [ ] 金絲雀與功能旗標下的驗證
- [ ] 用可觀測性資料找出測試沒涵蓋的使用情境

### 4.6 測試策略與規劃

- [ ] 基於風險的測試：風險辨識、評估、排序
- [ ] 測試策略與測試計畫：兩份文件各回答什麼問題
- [ ] 測試估算與在時程壓力下取捨
- [ ] 上線準則與發布品質判斷
- [ ] 回歸測試策略：每次發布要測什麼

### 4.7 帶領品質工作

- [ ] 整個團隊對品質負責（whole-team quality）：QA 怎麼賦能開發者
- [ ] 測試流程改善：TMMi 與回顧
- [ ] 品質指標與向管理層報告
- [ ] 測試工具與框架的選型評估
- [ ] 建立 QA 團隊：招募、面試、培養
- [ ] 職涯路線與證照：ISTQB 各級與資深 QA 的成長方向

### 4.8 收尾

- [ ] 為短網址服務 v4 寫一份完整的品質策略：風險、分層、非功能、正式環境驗證與上線準則

| --- | --- | --- |
| L0 | 畫出功能與風險地圖 | 畫出功能與風險地圖 |
| L1 | 用設計技術推導「建立短網址」的案例 | 探索式測試、提交缺陷報告 |
| L2 | 單元、整合、API、契約測試 | REST API 測試、Playwright E2E |

| L4 | 效能、韌性、品質策略 | 無障礙稽核、前端效能 |
